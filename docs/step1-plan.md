## 1. ブランチの切り方

```
main  ──●6dec8ea────────●(STEP 2 マージ)───────────────────────●(STEP 3〜8 マージ＝本番移行)
          \            /           \                          /
           feature/safety-export     feature/field-mode ──●S3─●S4─●S5─●S6─●S7─●S8
           （STEP 2 のみ）            （STEP 2 マージ後の main から開始）
```

1. `feature/safety-export` を main から作成し、STEP 2 を1コミットで作る（確認で直しが出たら「STEP 2 修正: …」の追加コミット）。
2. push → Cloudflare のプレビュー URL で実機確認 → GitHub で PR を作成（私が作成）→ **あなたがマージ**（main への反映はあなたの操作 or 明示の指示があったときのみ）。
3. マージ後、本番（GitHub Pages）で**各端末・各ブラウザごとに**全データを書き出す（Android Chrome／iPhone Safari タブ／iPhone ホーム画面アプリはそれぞれ別保存場所）。
4. 現在の `feature/field-mode`（main と同一、独自コミットなし）を main に早送りしてから STEP 3〜8 を各1コミットで積む。
5. STEP 8 の確認が終わったら PR → マージ。この時点で初めて本番データに移行処理が走る。

push は各ステップの終わりに、あなたの了承を得てから行う。

## 2. Cloudflare Pages の設定手順（あなたの操作）

画面の表記は変わることがあるため、近い名前のボタンを選んでください。

1. https://dash.cloudflare.com で無料アカウントを作成・ログイン。
2. 左メニュー「Workers & Pages」→「作成（Create）」。
   Workers の画面が出た場合は、下部の「Pages を使う／Looking to deploy Pages?」のリンクから Pages 側へ。
3. 「Git に接続（Import an existing Git repository）」→ GitHub を選び連携を承認。
   アクセス範囲は「Only select repositories」で `shrine-checklist` だけにする。
4. `shrine-checklist` を選び「セットアップを開始」。
5. 設定値：
   - プロジェクト名：`shrine-checklist`（使用済みなら別名。URL が変わるだけ）
   - 本番ブランチ：`main`
   - フレームワーク プリセット：なし（None）
   - ビルドコマンド：空欄
   - ビルド出力ディレクトリ：`/`（エラーになる場合は `.`）
6. 「保存してデプロイ」。
7. プロジェクトの「設定 → ビルド → ブランチの制御（Branch control）」で、プレビューを
   「すべての本番以外のブランチ」または「カスタム：`feature/*`」に設定。
8. 確認に使う URL は**ブランチ別名 URL**：
   - STEP 2：`https://feature-safety-export.shrine-checklist.pages.dev`
   - STEP 3〜8：`https://feature-field-mode.shrine-checklist.pages.dev`

### 注意点
- デプロイごとに出る `https://ab12cd34.shrine-checklist.pages.dev` のような**ハッシュ付き URL は毎回別ドメイン＝別データ**。ホーム画面追加・テストデータが引き継がれないので使わない。必ずブランチ別名 URL を使う。
- 本番ブランチ main も `https://shrine-checklist.pages.dev` に公開されるが、GitHub Pages とは**別データ**。実記録には使わない（混乱防止のため、pages.dev 上では画面に「テスト版」バッジを出す。STEP 2 で実装）。
- プレビュー URL は誰でも開けるが、データは各端末内にしか無いので中身は漏れない。
- Cloudflare は `/index.html` を `/` へリダイレクトする。既存の service worker はリダイレクト応答を作り直す処理（`cleanResponse`）を持っているので問題ない想定だが、STEP 2 の確認項目に入れる。
- プレビューで iPhone の「ホーム画面に追加」をすると、本番とは別アプリとして並ぶ。テスト版バッジで区別する。

## 3. データ設計

### 3.1 保存場所の全体像

すべて `shrine-` で始める（`nobwat.github.io` は他リポジトリとオリジンを共有するため衝突回避）。

| 保存先 | キー／DB | 中身 | 追加ステップ |
|---|---|---|---|
| localStorage | `shrine-entries-offline` | 記録の配列（既存。外側は配列のまま） | 既存 |
| localStorage | `shrine-entries-offline_backup_v1_20261020T103000` | 移行・読み込み前の丸ごと複製（最新3件まで） | STEP 2/3 |
| localStorage | `shrine-settings` | 設定（写真サイズ、録音上限、時間帯境界、位置の丸め） | STEP 2 |
| localStorage | `shrine-meta` | 最後のバックアップ日時、移行ログ | STEP 2 |
| localStorage | `shrine-errorlog` | 直近のエラー10件 | STEP 2 |
| IndexedDB | DB `shrine-checklist` | メディアのメタ情報・本体・録音途中チャンク | STEP 3 |

写真・音声のバイナリは IndexedDB のみ。localStorage には入れない。

### 3.2 記録（localStorage 配列の1要素）— schemaVersion 2

既存フィールドは**削除・改名・型変更しない**（`updatedAt` も数値ミリ秒のまま）。下記は追加分。

```jsonc
{
  // ---- 既存（そのまま） ----
  "id": "s_m1x2k3ab9f",
  "name": "○○神社",
  "checks": { "b1": true },
  "visit": { "v_date": "2026-10-17", "v_weather": "晴れ 18℃", "v_timeband": "日中", "v_spot_torii_chk": true },
  "updatedAt": 1760670000000,

  // ---- 追加 ----
  "schemaVersion": 2,
  "status": "final",                 // "final" | "draft"（既存記録は移行で "final"）
  "createdAt": "2026-10-17T10:23:45+09:00", // 新規作成分のみ。既存記録には付けない（不明なため）

  "field": {                         // 現地モードで作った記録だけが持つ
    "startedAt": "2026-10-17T10:23:45+09:00", // 現地モード開始（端末時刻・時差付き）
    "visitAt":   "2026-10-17T10:23:45+09:00", // 参拝日時（あとで修正可）
    "location": {
      "lat": 35.681236, "lon": 139.767125, "accuracyM": 12,
      "status": "ok",                // ok | denied | timeout | unavailable | manual
      "fetchedAt": "2026-10-17T10:23:52+09:00"
    },
    "weather": {
      "code": 1, "label": null, "tempC": 18.2, "precipitationMm": 0,
      "source": "open-meteo",
      "basis": "current",            // current | hourly | archive（どのAPIの値か）
      "status": "ok",                // ok | pending | failed | manual
      "fetchedAt": "2026-10-17T10:23:55+09:00",
      "lastTriedAt": "2026-10-17T10:23:55+09:00"
    }
  },

  "autoFill": {                      // 既存の記録画面に自動で入れた値の記録
    "v_date":     { "value": "2026-10-17", "state": "auto",   "at": "…" },
    "v_timeband": { "value": "日中",        "state": "auto",   "at": "…" },
    "v_weather":  { "value": "晴れ 18℃",   "state": "manual", "at": "…" }
  },

  "autoChecks": {                    // 写真ラベルから自動で付けたチェック
    "v_spot_torii_chk": { "mediaId": "6f1c…", "at": "…" }
  }
}
```

**天候 `label` の扱い**：自動取得時は `null` とし、表示時に WMO コード→日本語の変換表で生成する。`label` に文字が入るのは手入力（`status: "manual"`）のときだけ。

**「自動」バッジの判定**：`visit[項目] === autoFill[項目].value` かつ `state === "auto"` のときだけ表示する。
- 新しいコードで手で直したら、`state` を `"manual"` に変える。以後、その項目には二度と自動値を入れない（空欄に戻しても入れない）。
- 古い版のアプリで手で直された場合も、値の比較で自動ではないと判定できる。

**自動値を入れるタイミング**：現地モード開始時と、天候の取得に成功した時だけ（画面を表示するたびには入れない）。条件は「`visit[項目]` が空欄」かつ「`state` が manual でない」こと。

### 3.3 メディア（IndexedDB）

DB 名 `shrine-checklist`、バージョン 1。

| ストア | keyPath | インデックス | 中身 |
|---|---|---|---|
| `media` | `id` | `visitId`, `createdAt` | メタ情報（一覧表示はここだけ読む） |
| `blobs` | `id` | — | `{ id, blob, thumb }`（写真は320pxのサムネイルも持つ） |
| `recChunks` | `[recId, seq]` | `recId` | 録音中の1秒ごとのチャンク（アプリが落ちたときの回収用） |
| `kv` | `key` | — | IndexedDB 側のメタ情報（DB作成日時など） |

`media` の1件：

```jsonc
{
  "id": "6f1c2b7e-…",              // UUID（crypto.randomUUID。無い端末は getRandomValues で生成）
  "visitId": "s_m1x2k3ab9f",       // 記録の id
  "type": "photo",                 // photo | audio | memo
  "seq": 3,                        // その記録内での連番（zip のファイル名用）
  "createdAt": "2026-10-17T10:25:01+09:00", // 端末時刻
  "updatedAt": "…",
  "mimeType": "image/jpeg",
  "ext": "jpg",
  "size": 612345,
  "width": 2048, "height": 1536,   // 写真のみ
  "durationSec": 42.0,             // 音声のみ（経過時間から計算）
  "label": "torii",                // 写真のみ。キーで保存（下表）。未分類は null
  "text": null,                    // メモのみ
  "interrupted": false,            // 音声：画面ロック等で自動停止したか
  "exifStripped": true             // 写真：canvas 再エンコード済みか
}
```

メタ情報と本体は**同じトランザクション**で書く（片方だけ残る状態を作らない）。

### 3.4 写真ラベル対応表（1か所の定数で管理）

ラベルはキーで保存し、表示名や対応チェックは表から引く。

| key | 表示名 | 自動チェック先 |
|---|---|---|
| `signage` | 案内板・由緒書き | `v_chk_signage` |
| `map` | 境内図 | `v_chk_map` |
| `torii` | 鳥居 | `v_spot_torii_chk` |
| `haiden` | 拝殿・本殿 | `v_spot_haiden_chk` |
| `komainu` | 狛犬 | `v_spot_komainu_chk` |
| `shinboku` | 御神木・名木 | `v_spot_shinboku_chk` |
| `toro` | 灯籠・石碑・伝承の石 | `v_spot_toro_chk` |
| `juyohin` | お守り・おみくじ | `v_chk_juyohin` |
| `other` | その他 | `v_spot_other_chk` |
| `temizuya` | 手水舎 | （なし） |
| `goshuin` | 御朱印 | （なし） |

**自動チェックの規則**

- ラベルを付けた時点で、対応チェックが未チェックなら付け、`autoChecks` に記録する。
- 既に手でチェック済みなら記録しない（取り消し対象にしない）。
- ラベルを外したり変えたりしても、チェックは外さない。
- 自動で付いたチェックを手で操作したら、`autoChecks` から外す（以後は手動扱い）。
- 「自動チェックを取り消す」ボタンは、`autoChecks` にある項目だけをまとめて外す。

### 3.5 設定（`shrine-settings`）

```jsonc
{
  "photoMaxEdge": 2048,            // 1600 | 2048 | "max"（max = canvas 上限まで）
  "audioMaxSec": 180,
  "timebands": { "early": "04:00", "day": "07:00", "evening": "16:00", "night": "19:00" },
  "roundLocationForApi": true      // 天候APIへ送る緯度経度を小数2桁（約1km）に丸める
}
```

- 時間帯の判定：開始時刻が `early ≤ t < day` なら早朝、`day ≤ t < evening` なら日中、`evening ≤ t < night` なら夕方、それ以外は夜（日をまたぐ）。
- 境界は昇順でないと保存できないようにする。

## 4. 移行処理（STEP 3）

### 4.1 変換内容（v1 → v2）

```
migrate(e) = e.schemaVersion >= 2 ? e : { ...e, schemaVersion: 2, status: "final" }
```

- 追加するのは2フィールドだけ。`field`／`autoFill`／`autoChecks` は必要になった記録にだけ後から付ける。
- 何度実行しても同じ結果になる（冪等）。
- 古い版のアプリが後から作った記録（`schemaVersion` なし）も、次回起動時に同じ処理で揃う。

### 4.2 手順（起動時に毎回実行。変更が無ければ何も書かない）

1. `shrine-entries-offline` の生文字列を読む。
   - 無い → 新規利用なので終了。
2. `JSON.parse`。
   - 失敗 → **何も書かずに停止**。赤い警告を出し、読み取り専用モードにする。診断画面から生文字列のまま書き出せるようにする。
3. 形式を検査する（配列か、各要素が `id` を持つオブジェクトか）。
   - 不正 → 2 と同じく停止。
4. メモリ上で変換する（元の配列は触らない）。
5. **自己検証**：件数・id の並びが同じか、元の各記録の全フィールドが変換後も完全一致するか（追加のみであること）を確かめる。
   - 不一致 → 停止・エラー表示。
6. 変更が1件も無ければ終了（バックアップも作らない）。
7. 元の生文字列を `shrine-entries-offline_backup_v1_<YYYYMMDDTHHmmss>` に書き、読み戻して一致を確認する。
   - 書けない（容量不足）・不一致 → **元データに書かずに停止**。「全データ書き出し」を案内する。
8. 変換後を元キーに書く（`setItem` は全部成功か全部失敗のどちらかなので、半端な状態にはならない）。
9. 読み戻して `parse` し、手順5と同じ検証をする。
   - 不一致 → メモリにある元の生文字列で書き戻してエラー表示。
10. バックアップを整理する（`_backup_` キーは新しい3件だけ残す）。整理は成功の後にだけ行う。
11. `shrine-meta.migrations` に結果（日時、件数、バックアップキー名）を記録し、診断画面に表示する。

**失敗時の動作**：アプリは開けるが保存はしない（読み取り専用）。画面上部に「データの更新に失敗しました。元のデータは変更していません。診断画面から全データを書き出してください」と出す。

IndexedDB を開けない場合（プライベートブラウズなど）：文字の記録は今までどおり使える。現地モードの写真・録音だけ「この環境では使えません」と表示する。

### 4.3 戻し方（失敗時・不具合時）

1. **アプリ内**：診断画面のバックアップ一覧で「この時点に戻す」。戻す直前の状態も、別のバックアップとして自動で残す。
2. **JSON から**：STEP 2 で書き出したファイルを「読み込み → 重複は上書き」で読み込む。
3. **コードを戻す**：main の該当マージを `git revert` する。データは追加だけなので、古いコードでも読める（古いコードは知らないフィールドを保持したまま保存する）。
4. **最終手段（PC の開発者ツール）**：`localStorage.setItem("shrine-entries-offline", localStorage.getItem("<バックアップキー>"))`

### 4.4 移行の確認ツール（STEP 3 で追加）

診断画面に「書き出しJSONと比較」を付ける。STEP 2 で書き出したファイルを選ぶと、次の項目を表示する。

- 件数
- 全記録の元フィールドの一致／不一致
- 追加されたフィールド

完了条件2（件数・内容が変わっていない）をスマホだけで確認できる。

## 5. リスク 3・6・7・20 の対処

### リスク3：複数タブでの上書き
- **差分保存に変える**：各画面は「どの記録のどの項目を変えたか」だけを持つ。保存時は localStorage の**最新の配列を読み直して**、その差分だけを当てて書く。別タブが別の項目・別の記録を変えていても消えない（同じ項目を同時に変えた場合のみ後勝ち）。
- `storage` イベントを受けたら一覧を読み直す。開いている記録が他で変わった場合は画面に反映し、「別の画面で更新された内容を読み込みました」と表示する。
- 記録の追加・削除も同じ方式（最新の配列に追加・最新の配列から削除）。
- 写真・音声（IndexedDB）はトランザクション単位なので、この問題は起きない。
- iPhone の Safari タブとホーム画面アプリは保存場所が別なので、互いに干渉しない（その代わりデータも共有されない）。

### リスク6：バックアップキーの容量
- 移行で変更があるときだけ作る（4.2 の手順6）。
- 移行と JSON 読み込みで作るバックアップは、合わせて最新3件まで残す。
- バックアップを書けなければ処理を中止し、元データには書かない。
- 診断画面に、各キーのサイズとバックアップ一覧（戻す／削除）を表示する。
- 文字だけの記録なら1件数KB程度で、3件残しても 5MB の上限には余裕がある想定。実際のサイズは STEP 2 の診断画面で確認する。

### リスク7：削除・リセットとメディア
- **「この神社を削除」**：確認ダイアログに「写真N枚・録音M本・メモK件も削除されます。先にzipバックアップをおすすめします」と出す。IndexedDB のメディアを先に1トランザクションで削除し、成功したら記録を削除する。IndexedDB の削除に失敗した場合は記録も消さずにエラー表示する。
- **「このタブをリセット」（①現地記録）**：`visit` と `autoFill`／`autoChecks` を空にする。写真・録音・メモと位置・天候（`field`）は残す。確認ダイアログにもその旨を書く。自動値はすぐには入れ直さず、「自動値を入れ直す」ボタンで入れる。
- **孤立メディアの整理**：古い版のアプリで削除された記録のメディアは IndexedDB に残る。診断画面に「どの記録にも属さないメディア N件」を表示し、zip で書き出すか削除するかを選べるようにする。

### リスク20：空の下書きがたまる
- 現地モードを開いたとき、6時間以内に始めた下書きがあれば**自動でその続きにする**。画面上部に「前回の下書きを続けています ［新しく始める］」と出す。
- それ以外のときは新しい下書きを作る。
- 写真・録音・メモが0件で、神社名も空の下書きは「空」とみなす（位置・天候だけでは中身ありにしない）。空の下書きは、現地モードを閉じたとき、新しい下書きを作るとき、アプリ起動時に自動で消す。
- 一覧では下書きに「下書き」バッジを付ける。確定するとバッジが消える。古い版のアプリでは普通の記録として見える（データは壊れない）。

## 6. 主要な動作仕様（実装時の詳細）

### 写真（STEP 4）
- `<input type="file" accept="image/*" capture="environment">` に加えて、小さめの「ギャラリーから選ぶ」（capture なし）を用意する。Android でカメラ起動中にブラウザが落ちた場合の逃げ道。
- 縮小は `createImageBitmap(file, {imageOrientation:'from-image'})` で行い、失敗したら `<img>` での読み込みに切り替える。
- 縮小サイズは長辺 `photoMaxEdge` 以下、かつ**総画素数 1,670万以下**（iOS の canvas 上限）。「元サイズ」はこの面積上限だけを適用する。
- 出力は `canvas.toBlob('image/jpeg', 0.8)`。再エンコードで EXIF は消える。
- サムネイル（長辺320px）も同時に作り、同じトランザクションで保存する。保存できたら「保存しました（写真3枚目）」と表示する。
- ×ボタン → 確認ダイアログ → メタ情報と本体を同じトランザクションで削除する。
- 処理後は ImageBitmap を解放し、object URL を破棄する（iPhone のメモリ対策）。

### 録音（STEP 4）
- マイクは `getUserMedia({audio:true})` で取得する（カメラ映像は使わない）。
- 形式は `audio/webm;codecs=opus` → `audio/mp4;codecs=mp4a.40.2` → `audio/mp4` → 指定なし の順に `isTypeSupported` で判定し、`recorder.mimeType` に入った実際の値を保存する。
- `start(1000)` で1秒ごとにチャンクを受け取り、**その都度 `recChunks` へ保存する**。アプリが強制終了されても、次回起動時にチャンクをつなげて「中断された録音」として回収する。
- `visibilitychange` で画面が hidden になったら停止し、それまでの分を保存する。再び表示されたら「録音が中断されました」と表示する。
- 上限（既定3分）に達したら自動停止し、「上限の3分に達したので保存しました」と表示する。
- 録音中は、画面全体の赤い枠、大きな経過時間、大きな「停止」ボタンを表示する。
- 停止後はマイクを解放する（マイク使用中の表示を消す）。
- マイクが拒否された（NotAllowedError）ら、端末別の設定手順を表示する。
  - iPhone：「設定 → アプリ → Safari → マイク → 許可」
  - Android：「アドレスバー左のアイコン → 権限 → マイク」、ホーム画面アプリは「アイコン長押し → アプリ情報 → 権限」
  - 正確な文言は実装時に実機の表記に合わせる。
- 補足：Chrome で録る webm は再生時間の情報を持たない。PC では Chrome か VLC で再生する想定。

### 一言メモ（STEP 4）
- タップで大きな入力欄（文字20px以上）を開く。「キーボードのマイクボタンで音声入力もできます」と表示する。
- 1文字目を入力した時点でメモ1件を作り、以後は1秒ごとに自動保存する（「保存」を押す前に閉じても消えない）。

### 位置（STEP 5）
- `getCurrentPosition({enableHighAccuracy:true, timeout:15000, maximumAge:60000})` を使う。応答が無いまま止まる端末に備えて、アプリ側でも20秒のタイマーを持つ。
- エラーコードとの対応：1 → denied、3 → timeout、2 またはAPIなし → unavailable。
- 精度を表示し、100m を超えたら「位置が粗い」と表示する。「もう一度取得」ボタンを付ける。緯度経度の手入力は `status: "manual"` にする。

### 天候（STEP 5）
- **開始時（オンライン）**：`https://api.open-meteo.com/v1/forecast?latitude=…&longitude=…&current=weather_code,temperature_2m,precipitation&timezone=Asia%2FTokyo` を呼ぶ。
- **再取得**（オフライン・失敗で pending になった記録）：アプリ起動時と `online` イベント時に行う。同じ記録への再試行は10分以上あける。
  - 参拝から5日未満：`/v1/forecast?...&hourly=weather_code,temperature_2m,precipitation&past_days=<日数>&forecast_days=1` で、参拝時刻の時（`YYYY-MM-DDTHH:00`）の値を使う。
  - 5日以上：`https://archive-api.open-meteo.com/v1/archive?...&start_date=<日>&end_date=<日>&hourly=...`。値が `null` なら pending のまま残す。
- 各リクエストは AbortController で10秒のタイムアウトを付ける。
- 送る緯度経度は小数2桁に丸める（設定で解除可）。
- `v_weather` を手入力済み、または `autoFill.v_weather.state === "manual"` なら、`weather.status = "manual"` にして自動取得を止める。
- 天候を表示する画面すべてに「Weather data by Open-Meteo.com」（https://open-meteo.com/ へのリンク、CC BY 4.0）を表示する。
- service worker は他のオリジンへのリクエストを横取りしないので、天候 API の応答はキャッシュされない（現状どおり）。

### 容量（STEP 2・4）
- `navigator.storage.persist()` を起動時と現地モード開始時に呼ぶ。結果は診断画面に表示する。
- `storage.estimate()` で残り容量を表示する。残りが 200MB 未満、または上限の10%未満なら警告する。
- `QuotaExceededError` が出たら「保存できませんでした。バックアップして古い写真を整理してください」と表示する。保存前のデータ（撮った写真など）は画面上に保持したまま、再試行できるようにする。

### zip（STEP 7）
- JSZip 3.10.1 を `vendor/jszip.min.js` に同梱し、ライセンス文も同梱する（MIT を選択）。必要なときだけ読み込む。service worker の事前キャッシュに入れる。
- 中身：
  - `manifest.json`（formatVersion: 1、appVersion、作成日時、ファイル一覧と mimeType/size）
  - `visit.json`（記録＋メディアのメタ情報）
  - `photos/<連番>_<表示名>.jpg`
  - `audio/<連番>.<ext>`
  - `memo.txt`
- 写真・音声は STORE（無圧縮）、JSON とテキストは DEFLATE で格納する。
- ファイル名は `YYYYMMDD_神社名.zip`。日付は visitAt → v_date → 作成日の順に使う。`\ / : * ? " < > |` と制御文字は `_` に置き換え、50文字までにする。名前が空なら「名称未設定」。
- **2段階のボタン**：「zipを作成」→ 完成したら「共有／保存」ボタンを表示 → 2回目のタップで `canShare({files})` が true なら `share`、false またはエラーなら `<a download>`。iOS では、ユーザー操作の直後でないと share を呼べないための対策。
- 全件書き出しは神社ごとのフォルダに分ける。メタ情報から合計サイズを先に計算し、200MB を超えるなら「神社ごとの書き出し」をすすめる。
- 復元：zip を選ぶ → manifest を検査 → 記録 id・メディア id の重複を数える → 「新規N件・重複M件：スキップ／上書き」を選ぶ → 先に IndexedDB、成功したら localStorage に書く。
- 最後のバックアップ日時は `shrine-meta.lastBackupAt` に記録し、一覧画面の下に表示する。30日を過ぎたら小さな文字で「前回のバックアップから30日以上たっています」と表示する。

### service worker（STEP 2 で最小限、STEP 8 で本対応）
- STEP 2：キャッシュ削除を `shrine-app-` で始まるものだけに限定し、名前を `shrine-app-v4` に上げる。
- STEP 8：
  - `shrine-app-v5` にする。
  - install 時の `skipWaiting()` をやめ、新しい版が待機中になったら「新しいバージョンがあります（タップで更新）」を表示する。タップで `SKIP_WAITING` を送り、`controllerchange` で再読み込みする。**録音中・保存中は再読み込みを延期する**。
  - `vendor/jszip.min.js` を事前キャッシュに追加する。
  - 補足：ページ本体はネットワーク優先なので、オンラインで開けば常に最新の index.html が表示される。この通知が主に効くのは、オフラインで開いた後と service worker 自体の更新時。

### バージョン表示
- `index.html` に `APP_VERSION` を1か所で定義し、一覧画面の下と診断画面に表示する。
- 番号の予定：STEP 2 = `1.1.0`、STEP 3〜8 の開発中 = `2.0.0-dev.3` 〜 `2.0.0-dev.8`、本番 = `2.0.0`。
- service worker のキャッシュ名も同時に上げる。リリース時の確認項目に入れる。

## 8. 確認していただきたい点（STEP 2 着手前）

1. **位置の丸め**：天候 API に送る緯度経度を小数2桁（約1km）に丸めることを既定にしてよいか。天候の精度への影響はほぼない。
2. **写真を読み込めない場合**：一部の Android の HEIC など、縮小処理ができない写真をどうするか。
   - 案A（推奨）：元ファイルのまま保存し、「位置情報（EXIF）が残っています」と表示する。Android のカメラ起動では写真がギャラリーに残らないことがあり、捨てると写真が失われるため。
   - 案B：保存せずにエラー表示する。
